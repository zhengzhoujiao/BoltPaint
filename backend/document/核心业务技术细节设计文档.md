# 核心业务技术细节设计文档

本文档用于记录和维护系统中的核心业务处理流程及关键技术实现细节。

## 1. 图片处理与展示流程

系统中对于 AI 生成的大图及用户上传的图片，采用了“原图 + WebP 缩略图”的分级策略，以平衡存储成本、页面加载性能和图片质量。

### 1.1 生成图片保存流程 (`backend/app/routers/generate.py`)
当通过 Gemini API 生成图片后，系统执行以下保存策略：

1. **原图保存**：
   - 将 API 返回的 Base64 图片数据解码，保存为 `.png` 格式。
   - 保留了 API 生成的原始分辨率和质量。
   - 文件命名规则：`{artwork_id}_{timestamp}.png`。

2. **缩略图生成 (Thumbnail)**：
   - 使用 `Pillow` (PIL) 库读取原始图像内存数据。
   - **尺寸限制**：计算等比例缩放，强行将最大宽度限制为 **800px**。
   - **格式转换与压缩**：采用 `Image.Resampling.LANCZOS` 高质量重采样算法缩放后，保存为 **WebP** 格式，并设置 `quality=85`。
   - 该操作通常能将几 MB 的 PNG 图片压缩到几十 KB。
   - 文件命名规则：`{artwork_id}_{timestamp}_thumb.webp`。

3. **数据存储**：
   - 在 MongoDB 的 `tasks` 和 `artworks` 集合中，同时保存原图 URL (`image_url`) 和缩略图 URL (`thumbnail_url`)。

### 1.2 前端分级展示逻辑 (`webApp`)
前端充分利用了后端的双图策略，优化用户体验：

1. **信息流/列表页 (`ArtworkCard.tsx`)**：
   - **策略**：优先加载。
   - **实现**：`<img src={artwork.thumbnail_url || artwork.image_url || ''}>`
   - **效果**：瀑布流页面加载几十张图片时，由于读取的是体积极小的 WebP 缩略图，可以做到秒开且不卡顿。

2. **作品详情页 (`ArtworkDetail.tsx`)**：
   - **初次渲染**：中间主展示区域依然优先读取缩略图，确保详情页主体内容瞬间呈现。
   - **大图预览 (`ImagePreview.tsx`)**：当用户点击图片触发放大预览时，传入的是 `image_url` (原图 URL)。此时浏览器才会去下载原始高分辨率的 PNG 图片，支持用户双指/鼠标滚轮放大查看清晰细节。

### 1.3 用户长图上传自适应压缩 (`backend/app/routers/uploads.py`)
为了防止用户上传过大的参考图或头像占用过多带宽与算力，上传接口实现了自动防御机制：

1. **体积判定**：获取上传图片原始字节大小，若 **≤ 100KB**，直接保存原文件（可能是 PNG/JPG/WebP）。
2. **强制压缩（> 100KB）**：
   - 转换为 RGB 模式（忽略可能引起异常的透明通道）。
   - 按比例缩放：限制最大宽度为 **1200px**。
   - 转换为 WebP：使用 `quality=85` 尝试保存。
   - 极限压榨：若 85 质量仍超过 100KB，退级使用 `quality=75` 再次压缩。
   - 如果发生任何转换异常，则 fallback 回退保存原始二进制图片。

## 2. 用户上传图片限制与压缩机制

### 2.1 尺寸与大小限制
目前系统中对用户上传图片（主要指生图参考图、模板封面图）的限制如下：
- **前端上传限制**：已全线由 5MB 提升至 **20MB**（包含 `webApp` 创作页和 `manage` 管理后台）。由于引入了客户端预压缩，实际传输的数据包通常在 200KB 以内。
- **数量限制**：生图参考图目前限制最多上传 **3张**。

### 2.2 压缩执行位置与实现详情

1. **创作页生图参考图 (Reference Images)**：
   - **实现文件**：`webApp/utils/image.ts` (`compressImage` 函数)
   - **逻辑**：在调用 `generate` 接口前，前端直接读取 File 对象。使用 Canvas 进行等比例缩放（最大宽 1024px）并转换为 **WebP (0.8 质量)**。
   - **传输格式**：以 **Base64** 字符串形式嵌入 JSON 请求体发送给后端。
   - **后端处理**：`backend/app/services/storage.py` 中的 `save_reference_image` 直接将 Base64 转存为文件，不进行二次处理。

2. **管理后台模板/通用上传 (Cover/Avatar)**：
   - **实现文件**：`manage/src/utils/image.ts` (`compressImageToFile` 函数)
   - **逻辑**：由于后台上传接口通常使用 `multipart/form-data`，前端在压缩后会将 Base64 重新包装为 **Blob/File** 对象。
   - **传输格式**：标准的二进制文件流。
   - **后端处理**：`backend/app/routers/uploads.py` 接收文件。如果文件由于某些原因（如旧版浏览器不支持 WebP）导致压缩后体积仍 > 100KB，后端会执行**二次防御性压缩**（1200px 宽 WebP）。

### 2.3 设计考量 (Design Rationale)

*   **流量成本**：生图属于高频操作，手机端上传原图（3MB+）极其耗费流量。客户端压缩可减少 95% 以上的数据吞吐量。
*   **服务器响应速度**：后端处理 30MB 的 Base64 字符串会导致严重的 CPU 飙升和内存占用。将压力分散到用户设备上更具扩展性。
*   **一致性**：强制转换为 WebP 保证了存储端格式的统一，便于后续 CDN 缓存和优化。

## 3. 图片存储根目录（`OBJECT_STORAGE_DIR`）

本项目的图片存储在工程上指 **单一根目录**（如云盘挂载到服务器路径、NFS、容器 Volume 等），通过 **本地文件系统** 读写；**不经过** 阿里云 OSS / AWS S3 等对象存储 HTTP API。业务层只认 **URL 路径 + 相对文件名**，数据库中保存的是 **对外的逻辑路径**（如 `/generated/xxx.png`），而非服务器绝对路径。

### 3.1 配置项（`.env` / `app/config.py`）

| 含义 | 环境变量 | 说明 |
|------|-----------|------|
| 图片存储根目录 | `OBJECT_STORAGE_DIR` | **唯一**物理根。生产常见：`/lhcos-data`。未在环境中设置时，代码默认使用 **`backend/data`** 的绝对路径（便于本地开发）。**修改后需重启后端进程**。 |

`settings.uploads_dir` / `generated_dir` / `custom_dir` 均为 `os.path.join(object_storage_dir, "uploads"|"generated"|"custom")`。`object_storage_dir` 经校验会规范为 **`os.path.abspath`**。

### 3.2 目录与 URL 映射

磁盘子目录名与对外 URL 前缀如下（注意 **`uploads` 对应 URL 为 `/static/`，不是 `/uploads/`**）：

| 子目录 | HTTP 路径前缀 | 典型用途 |
|--------|----------------|----------|
| `uploads` | `/static/...` | 通用上传（封面、头像等，`uploads.py`） |
| `generated` | `/generated/...` | AI 生成原图与缩略图、扩图结果（`generate.py`、`expansion.py`） |
| `custom` | `/custom/...` | 参考图等（`save_reference_image`） |

进程启动时 `main.py` 的 `ensure_storage_dirs()` 会在上述三个子目录不存在时尝试创建（路径需可写）。

### 3.3 写入与读取

- **写入**：统一通过 **`get_active_dir(subdir)`**（等价于 `settings.*_dir`），落点包括：生成图、上传、参考图、扩图等。
- **读取**：**仅**在 `OBJECT_STORAGE_DIR` 下对应子目录查找。由 **`resolve_storage_file(subdir, rel_path)`** 完成，禁止路径成分 `..`，并校验结果落在该子目录根内，防止路径穿越。
- **HTTP**：`app/main.py` 中 `/static/`、`/generated/`、`/custom/` 使用 `resolve_storage_file` 返回 `FileResponse`。
- **服务端读参考图**：`generate.py` 使用同一 `resolve_storage_file`，与浏览器访问规则一致。

### 3.4 与 Nginx 的关系（`backend/docker/nginx/nginx.conf`）

仓库内 Nginx 将 `/static`、`/generated`、`/custom` **alias** 到 **`/lhcos-data` 下 `uploads` / `generated` / `custom`**，须与生产环境 **`OBJECT_STORAGE_DIR` 挂载路径一致**。若线上存储根不是 `/lhcos-data`，应同步修改 Nginx 中的 alias 或改为由后端代理静态（不推荐大流量场景）。

### 3.5 迁移与运维建议

- 若历史文件曾在其他目录（如旧版 `data`），需整体迁移至当前 `OBJECT_STORAGE_DIR` 下并保持子目录结构（`uploads` / `generated` / `custom`）不变，**URL 无需改**。
- 验收：对 `/generated/`、`/static/`、`/custom/` 各抽样一条可访问 URL。

## 4. 任务列表状态保持与无缝刷新机制

为了提升用户在任务列表页与任务详情页之间频繁切换的体验，系统在前端实现了一套基于 **SessionStorage + 后台静默刷新** 的状态保持方案，以替代传统的重新加载或较重的 KeepAlive 方案。

### 4.1 应用场景与目标
当用户从任务列表进入详情页（例如查看某个已完成的漫画任务），随后点击返回时：
- **目标**：页面必须瞬间恢复到离开前的状态（包括所在的 Tab 标签和精确的滚动位置），不能出现白屏 Loading，同时需要保证最终展示的数据是最新的。

### 4.2 技术实现细节 (`webApp/pages/Tasks.tsx`)

1. **状态持久化 (State Persistence)**
   - 使用 `sessionStorage` 缓存核心状态：`tasks_cache`（任务列表数据）、`tasks_activeTab`（当前激活的 Tab）、`tasks_scroll`（列表滚动距离）。
   - 监听 `tasks` 和 `activeTab` 的变化，并通过 `useEffect` 和事件处理函数实时同步到缓存中。

2. **状态初始化与即时渲染 (Instant Rendering)**
   - 在组件的 `useState` 初始化函数中，优先从 `sessionStorage` 同步读取并解析数据。
   - 如果检测到有效缓存，初始化时直接跳过全屏 Loading 状态，利用缓存数据完成首屏的“秒开”渲染。

3. **滚动位置精准恢复 (Scroll Restoration)**
   - 为滚动容器绑定 `ref` 和 `onScroll` 事件，实时将 `scrollTop` 写入缓存。
   - 组件挂载时，若存在滚动缓存，利用 `setTimeout` (如 50ms) 等待 React 完成初次 DOM 渲染后，将容器的 `scrollTop` 恢复至记录值。

4. **后台静默刷新 (Background Silent Refresh)**
   - 在利用缓存完成瞬间渲染后，`useEffect` 会立即触发一次 `loadTasks` 请求，并通过传入 `silent=true` 标志位来抑制界面的 Loading 动画。
   - 当最新数据返回后，触发状态更新，将最新的任务状态（如进度更新、状态流转）无缝平滑地合并到当前视图中。

### 4.3 设计优势考量
* **极致的用户体验**：瞬间恢复上下文，消除了网络延迟带来的等待焦虑，提供了类似 Native App 的流畅返回体验。
* **数据最终一致性**：在保证即时反馈的同时，通过静默刷新确保了数据的时效性，避免了纯缓存方案导致的数据陈旧问题（如长时间停留在“生成中”）。
* **轻量级与高可靠性**：相比于 React 的 KeepAlive（或离屏渲染）方案，SessionStorage 方案不需要在内存中长期驻留庞大的组件树和 DOM 节点，彻底杜绝了复杂路由切换下可能产生的内存泄漏和状态污染问题。

## 5. BoltPaint 支付宝直连架构

BoltPaint 国内部署后不再经过 Cutout 支付子站。订单、支付宝下单、支付通知和豆子发放均由 BoltPaint 后端完成。

### 5.1 发起支付
1. 用户在 `RechargeModal.tsx` 选择充值套餐。
2. 前端根据设备类型请求 `POST /orders/alipay/pay`，移动端使用 `pay_type=h5`，PC 端使用 `pay_type=page`。
3. 前端只提交 `package_id`；后端从 `recharge_packages` 读取金额和豆子数，创建 `pending` 订单并生成支付宝签名收银台地址。
4. 浏览器直接跳转支付宝，不经过 Cutout 页面或接口。

### 5.2 支付与回跳
* 移动端使用支付宝手机网站支付，可唤起支付宝 App。
* PC 端使用支付宝电脑网站支付，在支付宝收银台登录或扫码。
* 支付完成后，支付宝同步跳到 BoltPaint 后端 `GET /orders/alipay/return`；后端再重定向至 `PaymentResult.tsx`。

### 5.3 异步通知与发货
1. 支付宝 POST BoltPaint 后端 `POST /orders/alipay/notify`。
2. 后端验证 RSA2 签名，并核对 `app_id`、订单号和实付金额。
3. 订单从 `pending` 原子更新为 `paid`，再通过订单级幂等标记增加用户豆子，重复通知不会重复发放。
4. `PaymentResult.tsx` 轮询本地订单；订单仍为 `pending` 时，每 5 秒最多调用一次 `GET /orders/{order_id}/alipay/query` 主动查单，作为异步通知延迟或丢失的兜底。
